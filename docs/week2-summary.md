# 2주차 정리 — Rate Limit · 사용량 기록/통계 · React 개발자 포털

## 1. 목표

1주차에 만든 "API 키로 계좌 조회" 흐름 위에 **운영에 필요한 장치**와 **개발자가 쓰는 화면**을 붙인다.

```
핀테크 앱 ─X-API-Key─▶ [API 키 인증] ▶ [사용량 기록] ▶ [호출 제한(Redis)] ▶ 컨트롤러 ▶ bank_core
                                          │ (비동기)
                                          ▼
개발자 ─브라우저─▶ React 포털(5173) ─프록시─▶ /api/v1/apps/{appId}/usage ◀─ api_usage_logs(MySQL)
```

- **Rate Limit**: 앱마다 호출 한도를 두어, 한 앱이 너무 많이 불러 서비스 전체가 느려지는 것을 막는다. (초과 시 429)
- **사용량 기록 + 일별 통계**: 누가, 언제, 어느 API를, 어떤 결과로 불렀는지 남기고 개발자가 날짜별로 볼 수 있게 한다.
- **React 개발자 포털**: 회원가입·로그인·내 정보 화면을 만들어 curl 대신 브라우저로 쓸 수 있게 한다.

### 오픈 API 요청이 거치는 순서 (`OpenApiSecurityConfig`)

| 순서 | 필터 | 실패하면 |
|---|---|---|
| ① | `ApiKeyAuthenticationFilter` — 키 검사 | 401 (기록 안 함, 양동이 안 건드림) |
| ② | `UsageLogFilter` — 시간 재기 시작, 끝나면 finally에서 기록 | (실패 없음. 기록 실패는 버리고 WARN) |
| ③ | `RateLimitFilter` — 앱 양동이에서 토큰 1개 | 429 (②보다 안쪽이라 429도 기록됨) |
| ④ | 컨트롤러 → bank_core | 404 / 502 / 504 |

세 필터 모두 `@Component`가 아니라 `OpenApiSecurityConfig`에서 `new`로 만들어 `/open/v1/**` 규칙표에만 붙였다.
(빈으로 등록하면 Spring Boot가 모든 주소의 서블릿 필터로 자동 등록해, 인증보다 먼저 실행되어 버린다)

## 3. 핵심 설계 결정과 이유

| 결정 | 이유 | 대신 포기한 것 |
|---|---|---|
| **양동이 기준은 키가 아니라 앱(appId)** | 앱당 키를 2개까지 쓸 수 있다(키 교체용). 키마다 양동이를 주면 키 2개로 한도를 2배로 쓸 수 있다 | 키별로 다른 한도를 주는 기능 |
| **Lua 스크립트 + Redis 시계(`TIME`)** | 읽기→계산→쓰기 사이에 다른 요청이 끼면 같은 토큰을 둘이 꺼낸다. Redis는 스크립트 하나를 통째로 실행하므로 동시 100개에도 정확히 10개만 통과. 서버가 여러 대여도 시계가 하나 | 스크립트 디버깅이 Java보다 불편 |
| **Redis 키에 TTL(가득 차는 시간 × 2)** | 안 쓰는 앱의 키가 계속 쌓이지 않게. 그 시간 동안 요청이 없었다면 어차피 가득 찼을 것이라 지워도 결과가 같다 | — |
| **Redis 장애 시 fail-open + 명령 제한 시간 500ms** | Rate Limit은 보조 장치이고 인증은 이미 끝났다. Redis가 죽었다고 모든 계좌 조회를 막으면 피해가 더 크다. 대신 WARN 로그(appId만) | 장애 동안은 한도 없이 호출 가능 |
| **사용량 기록은 비동기 + 큐가 꽉 차면 버림** | DB 저장을 응답 스레드에서 하면 응답이 느려진다. 큐 크기를 제한하지 않으면 DB가 느려질 때 메모리가 바닥난다. 꽉 차면 기다리지 않고 바로 버린다(AbortPolicy) — 요청 스레드가 멈추면 안 되므로 | 기록 몇 건 유실 가능 (과금 근거로는 부족) |
| **다른 스레드에는 request가 아니라 불변 record(`UsageLogEntry`)를 넘김** | 요청이 끝나면 Tomcat이 request 객체를 다음 요청에 재활용한다. 나중에 읽으면 엉뚱한 값을 읽을 수 있다 | — |
| **endpoint는 실제 주소가 아니라 주소 틀로 저장** | `/open/v1/accounts/{accountNumber}`로 저장해 계좌번호가 DB에 남지 않는다. 주소별 통계를 묶기에도 좋다 | 어떤 계좌를 많이 조회했는지는 알 수 없음 (일부러) |
| **주소 틀은 Spring MVC 주소 목록을 직접 맞춰 봄** | 429는 컨트롤러까지 가지 않아 Spring이 주소 틀을 알려 주지 않는다. `RequestMappingHandlerMapping`의 목록을 `PathPattern`으로 맞춰 보면 200이든 429든 같은 틀이 나온다. 없으면 `UNMATCHED` | — |
| **통계는 조회 시 DB `GROUP BY`로 집계** | 기록 수십만 건을 Java로 가져오지 않고 날짜 수(최대 31줄)만 가져온다. 기간 조건을 `requested_at >= 시작 AND < 다음날 0시`로 써서 인덱스 `(app_id, requested_at)`를 쓸 수 있게 | 매우 커지면 미리 집계해 둔 테이블이 필요 |
| **시각은 `Clock` 빈(Asia/Seoul)** | 서버가 UTC여도 한국 날짜로 기록·집계. 테스트에서 시각을 고정해 자정 경계를 정확히 시험 | — |
| **Vite 프록시 `/api → 127.0.0.1:8081`** | 브라우저는 같은 주소(5173)로만 요청 → CORS 설정 없이 백엔드를 그대로 둠. `localhost` 대신 `127.0.0.1` (1주차 IPv4/IPv6 교훈) | 실제 배포 때는 같은 도메인으로 묶는 별도 설정 필요 |
| **토큰은 sessionStorage** | 탭을 닫으면 지워져 localStorage보다 오래 남지 않는다. 구현이 단순 | XSS가 생기면 스크립트가 토큰을 읽을 수 있음 |
| **API 호출은 `src/api.js` 한 파일** | 주소·헤더·오류 해석이 한곳에. 백엔드가 꺼졌을 때 프록시가 주는 "본문 없는 502"를 `{code}` 유무로 구분해 "서버에 연결할 수 없습니다"로 바꿈 | — |

### 실제 서버 확인 (curl)

- **Rate Limit**: 같은 키로 11번 → 200 ×10 (Remaining 9→0) + 429 (`Retry-After: 1`). Redis에 `ratelimit:app:{id}` = `tokens 0.27, ts …`, PTTL 약 20초.
- **사용량 기록**: ping 9번 + 계좌 조회 3번(502, 429, 429) + 가짜 키 1번(401) → DB에 12줄(401 없음), 429도 `/open/v1/accounts/{accountNumber}`로 기록, 계좌번호 저장 0건.
- **통계 API**: 11-20~11-26 7일이 모두 나오고 빈 날 0, 11-26 = total 12 / success 9 / rateLimited 2 / serverError 1, byEndpoint 2줄.
- **프록시(5173) 경유**: 회원가입 201·중복 409·형식 오류 400, 로그인 실패 401·성공 200, `/me` 200·틀린 토큰 401. 백엔드를 끄면 프록시가 본문 없는 502를 주고 `api.js`가 "서버에 연결할 수 없습니다"로 바꾸는 것까지 확인.
- **`npm run build`** 성공.

### 브라우저로 직접 확인 (내가 확인)

회원가입(성공·중복 이메일·짧은 비밀번호), 로그인(성공·실패), 내 정보, 로그아웃, 로그아웃 후 `/me` 차단, 서버 꺼짐 — 모두 정상.

## 5. 트러블슈팅

### 5-1. Redis 6379 포트가 이미 사용 중
- **증상**: `lsof -i :6379`에 `redis-server`가 보임.
- **원인**: 이 PC에 직접 설치된 Redis(brew 등)가 6379를 쓰고 있었다.
- **해결**: Docker Redis는 **6380**으로 열고(`127.0.0.1:6380:6379`), Spring의 Redis 주소도 `localhost`가 아니라 **`127.0.0.1`**로 적었다. 1주차 nginx 사건처럼 IPv4/IPv6가 다른 프로그램으로 갈리는 일을 막기 위해서.

### 5-2. "Redis 장애" 테스트가 제한 시간(500ms)을 검증하지 못함
- **증상**: 닫힌 포트로 만든 "Redis 꺼짐" 테스트는 연결이 **바로 거부**되어, 명령 제한 시간 설정이 맞는지는 확인되지 않았다.
- **해결**: 접속은 받지만 대답하지 않는 **블랙홀 서버**를 Redis 주소로 넣은 테스트를 추가. 경고 로그 간격이 약 0.6초로, 500ms 제한 시간이 실제로 동작함을 확인.

### 5-3. Redis가 없어야 하는 테스트에 Redis가 붙음
- **원인**: 공용 테스트 설정(`TestcontainersConfiguration`)의 `@ServiceConnection`이 `spring.data.redis.*` 설정보다 우선한다.
- **해결**: Redis 장애 테스트만 **MySQL만 띄우는 설정**(`MySqlOnly`)을 따로 쓴다.

### 5-4. 큐 꽉 참 테스트의 "7~8건 버림" 가정이 틀림
- **처음 생각**: 스레드 1개 + 큐 1칸에 10건을 넣으면, 타이밍에 따라 7~8건이 버려질 것.
- **실제**: `ThreadPoolExecutor`는 **첫 작업을 큐에 넣지 않고 새 스레드에 바로 넘긴다**. 1번은 스레드, 2번은 큐 1칸, 3~10번(**정확히 8건**)이 버려진다. 테스트를 정확한 값으로 고쳤다.
- **교훈**: 불확실하면 범위로 넓히기보다 동작 원리를 확인해서 정확한 값을 검사한다.

### 5-5. 백엔드가 꺼졌을 때 fetch가 실패하지 않음
- **증상**: 백엔드(8081)를 꺼도 브라우저의 `fetch`는 예외 없이 응답을 받는다.
- **원인**: 브라우저는 Vite 개발 서버(5173)까지는 닿았고, **Vite 프록시가 본문 없는 502**를 대신 돌려준다.
- **해결**: `api.js`에서 "5xx인데 우리 형식(`{code}`)이 없으면 서버에 못 닿은 것"으로 판단. curl로 실제 502 응답 모양을 확인한 뒤 규칙을 정했다.

### 5-6. `127.0.0.1:5173`으로는 화면이 열리지 않음
- **원인**: Vite 개발 서버가 IPv6 `[::1]:5173`에만 열린다.
- **해결**: 브라우저는 `http://localhost:5173`으로 접속. (프록시의 백엔드 쪽 주소는 반대로 `127.0.0.1:8081`로 고정)

| | 프론트 설계: 라이브러리 최소화(react-router-dom만), Vite 프록시, `api.js` 한 파일, sessionStorage, 오류별 문구, 토큰 로그 금지 |
| | AI가 바꾸거나 추가한 결정을 검토해 받아들일지 판단 (byEndpoint 형식 등) |
| | **브라우저로 7가지 시나리오 직접 확인**, 커밋 시점과 메시지 결정 |

## 7. 알려진 한계

- **가짜 키 요청은 횟수 제한이 없다.** Rate Limit은 인증된 앱 기준이라, 틀린 키로 계속 보내는 요청은 401로 끝나지만 제한 없이 매번 DB를 조회한다. → **IP 기준 제한**이 필요.
- **Redis 장애가 길어지면 요청마다 최대 0.5초가 늘어나고 WARN 로그가 쏟아진다.** → 일정 시간 Redis를 아예 건너뛰는 **서킷 브레이커**가 필요.
- **사용량 기록은 몇 건 유실될 수 있다.** 큐가 꽉 찼을 때, 저장에 실패했을 때, 서버 종료 때 5초 안에 다 저장하지 못했을 때. 통계용으로는 괜찮지만 **과금 근거로는 부족**하다.
- **요청 1건 = INSERT 1번.** 호출량이 많아지면 모아서 저장(배치 INSERT)해야 한다.
- **통계 인덱스는 데이터가 많을 때 확인하지 않았다.** 개발 DB EXPLAIN에서 인덱스는 선택됐지만 12줄뿐이라 전체 인덱스를 훑었다(`type=index`). 많은 데이터에서 범위 검색(`range`)이 되는지는 미확인.
- **sessionStorage는 XSS에 약하다.** 페이지에 악성 스크립트가 들어오면 토큰을 읽을 수 있다. → **HttpOnly 쿠키**로 옮기는 것을 검토.
- **React 화면에는 자동 테스트가 없다.** 브라우저 수동 확인과 `api.js` 실제 호출 확인만 했다.
- (1주차부터) 유효한 키만 있으면 연동 회원의 모든 계좌를 조회할 수 있다. 실제 오픈뱅킹은 고객 동의(OAuth)로 앱별 계좌 범위를 정한다.

## 8. 배운 개념

- **토큰 버킷**: 양동이 크기(capacity) = 한 번에 몰아 쓸 수 있는 양, 채우는 속도 = 평균 허용 속도. 고정 창(분당 N회)과 달리 창 경계에서 2배가 몰리는 문제가 없다.
- **경쟁 상태와 원자성**: "읽고 → 계산하고 → 쓰기"가 나뉘어 있으면 동시 요청이 같은 값을 읽는다. Redis Lua 스크립트는 통째로 실행돼 그 사이에 다른 명령이 끼지 않는다.
- **fail-open vs fail-closed**: 보조 장치(호출 제한)는 장애 시 열어 두고, 핵심 보안(인증)은 장애 시 닫는다.
- **필터 순서와 finally**: 바깥 필터의 `finally`는 안쪽 필터가 일찍 응답을 끝내도(429) 실행된다. 그래서 기록 필터를 제한 필터보다 바깥에 둔다.
- **스레드풀과 거절 정책**: `ThreadPoolExecutor`(고정 스레드 + `ArrayBlockingQueue`)와 `AbortPolicy`/`CallerRunsPolicy`의 차이, 첫 작업은 큐를 거치지 않는다는 것.
- **스레드 간 데이터 전달**: request처럼 재활용되는 객체 대신 불변 record를 넘긴다.
- **`Clock` 주입**: `LocalDateTime.now()`를 직접 부르지 않으면 테스트에서 시간을 마음대로 정할 수 있다.
- **반열린 구간과 인덱스**: `DATE(열) = ?`는 인덱스를 못 쓰고, `열 >= 시작 AND 열 < 끝`은 쓸 수 있다.
- **React 기초**: 컴포넌트, `useState`(값이 바뀌면 다시 그림), `useEffect`(그린 뒤 할 일, StrictMode에서 두 번 실행), `react-router-dom`(주소 → 화면).
- **CORS와 개발 프록시**: 브라우저는 다른 출처로의 요청을 막는다. 개발 서버 프록시로 같은 출처처럼 보이게 한다.

## 9. 면접 꼬리 질문

1. **Rate Limit 기준을 왜 API 키가 아니라 앱으로 했나요?**
   → 앱당 키가 2개까지라 키 기준이면 한도를 2배로 쓸 수 있다. 꼬리: *IP 기준은?* → 인증 전 요청(가짜 키)을 막는 데 필요하고, 다음 단계로 생각하고 있다.
2. **Redis에서 GET 후 SET으로 하면 안 되나요?**
   → 동시 요청이 같은 토큰 수를 읽어 둘 다 통과한다. Lua 스크립트로 원자적으로 처리했고, 동시 100개 → 정확히 10개 통과로 검증했다.
   - 꼬리: *시간은 왜 Redis `TIME`?* → 서버가 여러 대면 서버 시계가 조금씩 달라 토큰 계산이 어긋난다.
3. **Redis가 죽으면 어떻게 되나요? 왜 그렇게 정했나요?**
   → fail-open(통과) + WARN. 인증은 이미 끝났고, 보조 장치 때문에 전체 서비스가 멈추면 안 된다. 명령 제한 시간 500ms로 오래 붙잡히지 않게 했고, 블랙홀 서버 테스트로 확인했다. 꼬리: *계속 죽어 있으면?* → 서킷 브레이커.
4. **사용량 기록을 왜 비동기로 했고, 유실은 괜찮나요?**
   → 응답 지연을 막기 위해. 큐 크기를 제한해 메모리를 보호하고, 꽉 차면 버린다. 통계용이라 감수했지만 과금용이면 메시지 큐(Kafka 등)나 로컬 파일 버퍼가 필요하다.
5. **429로 막힌 요청은 컨트롤러에 안 가는데, 주소 틀을 어떻게 알았나요?**
   → Spring MVC의 주소 목록(`RequestMappingHandlerMapping`)을 `PathPattern`으로 직접 맞춰 본다. 결과와 상관없이 같은 방법이라 같은 주소는 늘 같은 틀.
6. **왜 실제 주소를 저장하지 않았나요?**
   → 계좌번호가 DB에 남으면 개인정보 유출 위험이 커진다. 통계도 주소 틀 기준이 더 유용하다.
7. **통계를 미리 집계하지 않고 조회할 때 GROUP BY 하는 이유는? 언제 바꾸나요?**
   → 지금 규모에서는 단순하고 정확하다. 기록이 수천만 건이 되면 일별 집계 테이블을 배치로 만들어 둔다.
8. **프론트에서 토큰을 어디에 저장했고, 위험은?**
   → sessionStorage. XSS가 있으면 읽힌다. HttpOnly 쿠키로 옮기면 스크립트가 못 읽지만 CSRF 대비가 필요하다.
9. **백엔드가 꺼졌을 때 "서버에 연결할 수 없습니다"를 어떻게 구분했나요?**
   → 개발 환경에서는 프록시가 본문 없는 502를 준다. 우리 서버 오류는 항상 `{code}`가 있으므로 그것으로 구분했다.
