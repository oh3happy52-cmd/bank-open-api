# 3주차 정리 — 이체 API · 웹훅(아웃박스·HMAC 서명·재전송) · 모의 핀테크 서버 · 내 앱 화면

## 1. 목표

조회만 되던 오픈 API에 **돈이 움직이는 기능(이체)** 을 붙이고, 이체가 끝나면 핀테크 앱에 **알림(웹훅)** 을 보낸다.
돈이 걸린 기능이라 "두 번 나가지 않게", "알림이 사라지지 않게", "가짜 알림을 구분할 수 있게"가 핵심이다.

```
핀테크 앱 ─X-API-Key + Idempotency-Key─▶ [인증·사용량·호출 제한] ▶ TransferController
                                                                      │ "app-{appId}:{키}"
                                                                      ▼
                                                                  bank_core 이체 (201)
                                                                      │
                                        webhook_deliveries(PENDING) ◀─┘ 아웃박스에 1줄 저장
                                                │
                                  1초마다 발송 일꾼 (SKIP LOCKED + lease)
                                                │ POST + X-Webhook-Signature: v1=HMAC
                                                ▼
                             핀테크 서버 (로컬 실험: /mock-fintech/webhooks)
                             서명 검증 → 5분 시각 검사 → X-Webhook-Id 중복 제거
```

- **이체 API**: `POST /open/v1/transfers`. `Idempotency-Key`로 같은 요청을 다시 보내도 돈은 한 번만 옮겨진다.
- **웹훅**: 이체 성공을 DB(아웃박스)에 먼저 적고, 따로 도는 발송 일꾼이 서명해서 보낸다. 실패하면 간격을 늘려 다시 보낸다.
- **모의 핀테크 서버**: 웹훅을 "받는 쪽"이 해야 할 일(서명 검증·중복 제거)을 직접 구현하고, 장애를 일부러 일으켜 재전송을 실험한다.
- **React 내 앱 화면**: 앱 목록·등록, 앱 상세, API 키 발급(원문 1회 표시)·폐기.

## 3. 핵심 설계 결정과 이유

### 이체

| 결정 | 이유 | 대신 포기한 것 |
|---|---|---|
| **bank_core에는 `app-{appId}:{원래 키}`로 전달** | 모든 앱이 bank_core의 연동 회원 한 명으로 이체한다. A앱과 B앱이 우연히 같은 키 `order-1`을 쓰면 bank_core는 B앱 이체를 A앱 이체의 재전송으로 보고 A앱 결과를 주거나 422로 거절한다. 앱 번호를 붙여 키 공간을 앱마다 나눈다 | bank_core DB에서 키가 원래 모양과 조금 다르게 보임 |
| **붙여서 64자를 넘으면 `app-{appId}:~{SHA-256 지문}`** | bank_core 키 열이 64자. 지문은 같은 입력이면 항상 같아 재요청 멱등성이 그대로 유지되고, `~`는 원래 키에 쓸 수 없는 글자라 짧은 키와 절대 겹치지 않는다 | 긴 키는 bank_core에서 사람이 읽을 수 없음 |
| **bank_core 403/404 → 같은 404 `ACCOUNT_NOT_FOUND`** | "남의 계좌"와 "없는 계좌"를 구분해 주면 계좌가 존재하는지 알아낼 수 있다. 본문도 글자 하나까지 같게 | 앱 개발자가 원인을 정확히 알기 어려움 |
| **타임아웃(504)은 자동 재전송하지 않고 "같은 키로 재시도" 안내** | 타임아웃은 "실패"가 아니라 "결과를 모름"이다. bank_core에서는 이미 돈이 옮겨졌을 수 있다. 우리가 몰래 다시 보내기보다, 앱이 **같은 키**로 다시 보내면 bank_core 멱등성이 처음 결과를 돌려줘 이중 이체가 생기지 않는다 | 앱이 재시도 로직을 직접 가져야 함 |
| **bank_core 401은 재로그인 후 같은 키로 1번만 재시도** | bank_core는 토큰 검사를 이체 처리보다 먼저 하므로 401이면 돈은 옮겨지지 않은 상태 → 안전하게 다시 보낼 수 있다. 같은 키라 혹시 처리됐어도 중복 없음. 새 토큰도 401이면 무한 반복하지 않고 502 | — |
| **bank_core 오류 메시지 원문은 쓰지 않음** | 계좌번호가 섞여 있을 수 있다. 상태와 code만 받아 우리 `ErrorCode` 문구로 응답, 모르는 code는 같은 상태의 기본 code + WARN | bank_core의 자세한 설명 |
| **로그는 계좌번호 끝 4자리, 원래 키, 금액, 상태만** | 계좌번호 전체·토큰은 로그에 남기지 않는다 (2주차 "주소 틀 저장"과 같은 원칙) | — |

### 웹훅 (보내는 쪽)

| 결정 | 이유 | 대신 포기한 것 |
|---|---|---|
| **비밀키는 해시가 아니라 AES-256-GCM 암호문으로 저장** | API 키는 "맞는지 비교"만 하면 되니 해시로 충분했지만, 웹훅 비밀키는 **서명할 때마다 원문이 필요**하다 → 되돌릴 수 있는 암호화. GCM은 암호문이 바뀌면 복호화가 실패해 변조를 알 수 있다 | 암호화 키가 새면 모든 비밀키가 풀림 |
| **앱 번호를 AAD(추가 인증 데이터)로 넣음** | DB에서 A앱 암호문을 B앱 줄로 옮겨 붙여도 복호화가 실패한다 | — |
| **암호화 키는 `.env`의 `WEBHOOK_ENCRYPTION_KEY`** | DB가 통째로 새도 키가 따로 있어야 풀 수 없다. 없거나 32바이트가 아니면 서버가 시작되지 않음(잘못된 설정을 일찍 발견) | 키를 바꾸면 모든 앱이 비밀키를 다시 발급해야 함 |
| **아웃박스 테이블 + 1초 발송 일꾼** | 이체 응답 중에 바로 보내면 받는 쪽이 느릴 때 이체 응답도 느려지고, 서버가 죽으면 알림이 사라진다. DB에 먼저 적으면 **재시작해도 알림이 남아** 이어서 보낸다 | 최대 1초 늦게 도착 |
| **`FOR UPDATE SKIP LOCKED` + lease, HTTP 중에는 잠금 안 잡음** | 꺼내기(잠금 → `next_attempt_at = 지금+2분` → 커밋) / HTTP 보내기(트랜잭션 없음) / 결과 기록을 나눴다. 받는 쪽이 느려도 DB 연결·잠금을 쥐고 있지 않는다. 일꾼이 여럿이어도 같은 줄을 둘이 꺼내지 않고, 보내다 죽으면 lease가 지난 뒤 다른 일꾼이 다시 보낸다 | lease(2분) 동안은 재전송이 늦어짐 |
| **`UNIQUE(app_id, transfer_id, event_type)`** | 같은 `Idempotency-Key` 재요청으로 bank_core가 같은 이체 결과를 또 줘도 알림은 1줄만 생긴다 | — |
| **payload는 저장할 때 확정(스냅샷), `eventId`는 재전송해도 그대로** | 받는 쪽이 `X-Webhook-Id`로 중복을 거를 수 있다 | — |
| **서명 `v1=hex(HMAC-SHA256(비밀키, 타임스탬프 + "." + 본문))`** | 비밀키를 아는 우리만 만들 수 있고, 본문이 한 글자라도 바뀌면 맞지 않는다. 타임스탬프를 서명에 넣어 받는 쪽이 오래된 알림을 거를 수 있다. `v1=`로 나중에 방식을 바꿀 여지 | — |
| **재시도 2·4·8·16·32초(지수 백오프), 6번 실패 → FAILED** | 받는 쪽이 잠깐 죽었을 때 몰아서 때리지 않고 점점 간격을 늘린다. 끝없이 보내지 않도록 상한 | 약 1분 넘게 죽어 있으면 알림을 포기 (전송 기록 API로 확인) |
| **2xx만 성공, 3xx는 실패이고 리다이렉트를 따라가지 않음, 응답 본문은 읽지 않음** | 리다이렉트를 따라가면 등록하지 않은 주소로 갈 수 있다. 응답 본문은 크기도 내용도 알 수 없다 | — |
| **보낼 때 웹훅이 꺼져 있으면 CANCELED** | 꺼 둔 앱에 계속 보내지 않는다 | 다시 켜도 지난 알림은 안 감 |
| **비밀키 교체(rotate) 후 재전송은 새 키로 서명** | 서명은 저장할 때가 아니라 **보내는 순간** 한다. 옛 키는 바로 무효 | 교체 직후 받는 쪽이 아직 옛 키면 401 (겹치는 기간 없음) |

### 웹훅 (받는 쪽 — 모의 핀테크 서버)

| 결정 | 이유 |
|---|---|
| **본문을 `byte[]`로 받아 원본 바이트로 서명 검증** | JSON으로 읽었다가 다시 문자열로 만들면 칸 순서·공백이 달라져 서명이 맞지 않는다 |
| **상수 시간 비교(`MessageDigest.isEqual`)** | `equals`는 다른 글자에서 바로 멈춰 응답 시간 차이로 서명을 한 글자씩 맞혀 가는 타이밍 공격이 가능 |
| **타임스탬프가 5분 넘게 차이 나면 401** | 가로챈 알림을 나중에 그대로 다시 보내는 재전송 공격 방지 (딱 5분은 통과) |
| **`X-Webhook-Id`로 중복 제거, 중복이면 200 + `duplicateCount`만 +1** | 보내는 쪽은 at-least-once라 같은 알림이 또 올 수 있다. 중복에 500을 주면 계속 재전송된다 |
| **순서: 서명 → 시각 → (지연) → (failRate 500) → 중복 확인·기록 → (failAfterProcessing 500)** | 검증 안 된 요청으로는 아무 상태도 바꾸지 않는다. `failAfterProcessing`은 "처리는 했는데 응답이 실패"인 가장 까다로운 경우를 흉내 |
| **`mock-fintech.enabled`(기본 true, 운영 false) + 로그에 비밀키·서명값·본문 금지** | 인증 없는 실험용 API라 운영에서는 아예 빈을 만들지 않는다 |

### 화면

| 결정 | 이유 | 대신 포기한 것 |
|---|---|---|
| **키 원문은 모달에서 1번만, state에만** | sessionStorage·localStorage·console·URL에 넣지 않는다. 모달을 닫거나 화면을 떠나면 React가 state를 버려 원문이 어디에도 남지 않는다. 읽기 전용 입력칸 + 복사 버튼 + "닫으면 다시 볼 수 없습니다" 경고 | 잃어버리면 새로 발급해야 함 |
| **`RequireAuth`를 감싸는 Route(보호 라우트)** | `/apps`, `/apps/:appId`, `/me`가 같은 보호 규칙·메뉴를 공유. 토큰이 없으면 그리지 않고 `/login`, 서버가 401을 주면 토큰을 지우고 `/login` | — |
| **남의 앱·없는 앱은 같은 "앱을 찾을 수 없습니다"** | 서버의 404 원칙을 화면에서도 그대로 | — |

## 5. 트러블슈팅

### 5-1. 웹훅 암호화 키가 없어 실제 서버가 시작되지 않음
- **증상**: 웹훅 기능을 넣은 뒤 `./gradlew bootRun`을 하자 서버가 시작 단계에서 멈췄다. (테스트는 테스트용 설정에 키가 있어 통과했었다)
- **원인**: 내 `.env`에 `WEBHOOK_ENCRYPTION_KEY`를 아직 넣지 않았다. `WebhookSecretCipher`는 키가 없거나 32바이트가 아니면 **일부러 시작을 실패**시킨다.
- **확인 방법**: `.env`를 화면에 그대로 띄우지 않고, `grep`으로 **키 이름만** 있는지 확인하고 값은 `sed`로 가려서 봤다. (비밀값이 터미널·기록에 남지 않게)
- **해결**: `openssl rand -base64 32`로 만든 값을 `printf '\nWEBHOOK_ENCRYPTION_KEY=...'`로 추가했다. 맨 앞에 `\n`을 넣은 이유는 파일 마지막 줄에 줄바꿈이 없으면 **앞줄 값 뒤에 붙어 버려** 두 변수가 모두 망가지기 때문. 재시작 후 정상.
- **배운 점**: 필수 비밀값이 없으면 "일단 켜지고 나중에 이체 때 터지는" 대신 **아예 안 켜지게** 한 설계가, 실제로 문제를 첫 실행에서 바로 드러냈다.

### 5-2. 전체 테스트 15분 → 4분, 그리고 MySQL 강제 종료(OOM)로 18개 실패
- **증상 1 (느림)**: 웹훅·모의 서버 테스트를 추가하면서 `./gradlew test`가 약 **15분**까지 늘었다.
- **증상 2 (실패)**: 3단계(모의 핀테크 서버) 테스트를 추가한 뒤 18개가 DB 연결 오류로 실패했다.
- **원인 (둘이 같은 뿌리)**: 스프링 테스트는 설정(`@TestPropertySource`, 켜고 끈 기능 등)이 **같은 클래스끼리만** 테스트 환경(ApplicationContext)을 재사용한다. 설정이 조금씩 다른 테스트 클래스가 늘자 환경을 **여러 번 새로 띄웠고**(느림), 스프링은 만든 환경을 기본 **32개까지 닫지 않고 들고 있어서** 환경마다 붙은 MySQL·Redis 컨테이너가 계속 쌓였다. 결국 Docker Desktop 메모리 **약 4GB**를 넘어 MySQL이 OOM으로 강제 종료됐다(실패).
- **해결**:
  - `src/test/resources/spring.properties`에 `spring.test.context.cache.maxSize=4` — 4개를 넘으면 가장 오래 안 쓴 환경을 닫고 그 컨테이너도 멈춘다 → 동시에 떠 있는 MySQL이 최대 4~5개.
  - 테스트 설정 정리 — 클래스마다 조금씩 다르던 설정을 공용 테스트 설정(`src/test/resources/config/application.properties`)으로 모아 **같은 환경을 재사용하는 클래스를 늘렸다**.
  - 결과: 실패 0, 전체 약 **4분**(이번 정리 때 4분 14초).
- **교훈**: 테스트가 "가끔" 실패하거나 갑자기 느려지면 코드보다 먼저 자원(메모리·컨테이너 수)과 "환경이 몇 번 뜨는지"를 의심한다.

### 5-3. 웹훅과 모의 핀테크 서버를 기능별 커밋으로 나누기
- **상황**: 웹훅(2단계)과 모의 핀테크 서버(3단계) 코드가 한 번에 만들어져 작업 폴더에 같이 있었다. 한 커밋으로 묶으면 리뷰·되돌리기가 어렵다.
- **해결**:
  1. 모의 핀테크 파일(`mockfintech/` 코드·테스트, 관련 설정)을 **잠시 다른 곳으로 빼 두고**, 웹훅만 남긴 상태에서 전체 테스트 **143개 통과** 확인 → `fe0463c` 커밋.
  2. 빼 둔 파일을 되돌린 뒤 전체 테스트 **160개 통과** 확인 → `9bafaf4` 커밋.
- **왜**: 나중에 `git checkout`이나 `git bisect`로 **어느 커밋 시점으로 가도 빌드·테스트가 통과**해야 문제를 찾을 수 있다. 커밋만 나누고 테스트를 안 돌리면 중간 커밋이 깨진 상태일 수 있다.

### 5-4. 앱 번호를 붙이면 Idempotency-Key가 bank_core 길이(64자)를 넘음
- **증상**: 우리도 키를 64자까지 받으므로 `app-3:` + 64자 = 70자 → bank_core가 거절.
- **해결**: 64자를 넘을 때만 `app-{appId}:~{SHA-256 지문}`으로 바꿨다. 같은 키 → 같은 지문이라 재요청 멱등성 유지, `~`는 원래 키에 못 쓰는 글자라 짧은 키와 겹치지 않음. 경계(정확히 64자·65자)와 앱 번호 최댓값(19자리)을 테스트로 확인.

## 7. 알려진 한계

- **알림은 at-least-once다.** 받는 쪽이 처리하고 응답만 실패하면 같은 알림이 다시 간다. → 받는 쪽은 반드시 `X-Webhook-Id`로 중복을 걸러야 한다.
- **이체 201과 알림 저장 사이에 서버가 죽으면 알림이 빠질 수 있다.** 돈은 bank_core에서 옮겨졌는데 우리 DB에는 아직 아웃박스 줄이 없는 순간이 있다(서로 다른 DB라 한 트랜잭션으로 묶을 수 없음). 앱이 같은 키로 다시 요청하면 그때 저장된다. → bank_core 쪽 이벤트를 받아 오거나, 정기적으로 이체 목록과 대조하는 장치가 필요.
- **SSRF 위험.** 웹훅 주소에 `127.0.0.1`·사설망(10.x, 192.168.x)·클라우드 메타데이터 주소도 등록할 수 있어, 우리 서버가 내부망으로 요청을 보내게 만들 수 있다. 로컬 실험(모의 서버) 때문에 지금은 허용. → 운영에서는 DNS 해석 결과까지 확인해 내부 주소를 차단하고 `webhook.allow-http=false`.
- **알림을 순서대로 하나씩 보낸다.** 일꾼 한 바퀴에 최대 20개를 차례로 보내므로 느린 앱 하나가 다른 앱의 알림까지 늦춘다. → 앱별로 나누거나 병렬로 보내기.
- **payload에 계좌번호 전체가 DB에 쌓인다.** 받는 앱이 필요로 해서 넣었지만 `webhook_deliveries`가 계속 커지고 개인정보가 남는다(전송 기록 API에는 payload를 내보내지 않음). → 보관 기간이 지난 줄을 지우거나 payload를 비우는 정리 작업 필요.
- **모의 핀테크 서버 관리 API에 인증이 없다.** 누구나 비밀키를 넣고 장애를 켤 수 있다. → 운영에서는 `MOCK_FINTECH_ENABLED=false`로 반드시 끈다.
- (2주차부터) 가짜 키 요청 횟수 제한 없음, React 화면 자동 테스트 없음.

## 8. 배운 개념

- **멱등성(Idempotency)**: 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다. 키의 "범위(누구의 키인가)"까지 설계해야 한다.
- **타임아웃 = 결과를 모름**: 실패와 다르다. 돈이 걸린 요청은 자동 재시도보다 멱등 키로 안전하게 재시도하게 한다.
- **해시 vs 암호화**: 비교만 하면 해시(되돌릴 수 없음), 원문이 다시 필요하면 암호화(키로 되돌림). AES-GCM의 IV(매번 새로)·인증 태그·AAD.
- **HMAC 서명**: 비밀키를 아는 사람만 만들 수 있는 "본문 지문". 타임스탬프를 함께 서명해 재전송 공격을 막는다.
- **아웃박스 패턴**: 보낼 일을 먼저 DB에 적고, 따로 보낸다. 재시작해도 사라지지 않는다.
- **`FOR UPDATE SKIP LOCKED`와 lease**: 여러 일꾼이 같은 줄을 동시에 꺼내지 않게, 그리고 외부 호출 동안 잠금을 쥐지 않게.
- **지수 백오프**: 실패할수록 간격을 두 배로. 장애 난 상대를 몰아서 때리지 않는다.
- **at-least-once + 받는 쪽 중복 제거 = 사실상 exactly-once 효과**.
- **상수 시간 비교와 타이밍 공격**.
- **SSRF**: 사용자가 준 주소로 서버가 요청을 보내면 내부망이 노출될 수 있다.
- **React**: Context(`useAuth`), 감싸는 Route(보호 라우트 + `<Outlet />`), 민감한 값은 state에만.
- **테스트 환경 캐시**: 스프링 테스트는 설정이 같으면 환경을 재사용하고, 다르면 새로 만든다 → 컨테이너 수와 메모리.

## 9. 면접 꼬리 질문

1. **여러 앱이 같은 Idempotency-Key를 쓰면 어떻게 되나요?**
   → bank_core에는 모든 앱이 같은 회원으로 보이므로 충돌한다. `app-{appId}:{키}`로 앱마다 키 공간을 나눴다. 꼬리: *64자를 넘으면?* → SHA-256 지문으로 바꾸고 `~` 표시로 짧은 키와 겹치지 않게 했다.
2. **이체가 타임아웃 나면 서버가 알아서 다시 보내면 안 되나요?**
   → 타임아웃은 "결과를 모름"이라 이미 처리됐을 수 있다. 504와 함께 같은 키로 재시도하라고 안내하고, 같은 키면 bank_core가 처음 결과를 돌려준다. 꼬리: *401은 왜 재시도해도 되나요?* → bank_core가 토큰 검사를 이체보다 먼저 하므로 401이면 돈이 안 옮겨졌다. 그래도 같은 키로 보낸다.
3. **웹훅 비밀키는 왜 API 키처럼 해시로 저장하지 않았나요?**
   → 서명할 때 원문이 필요하다. AES-256-GCM으로 암호화하고 앱 번호를 AAD로 넣었다. 꼬리: *암호화 키를 바꾸려면?* → 지금은 모든 앱이 비밀키를 재발급해야 한다. 키 버전(`v1:`)을 붙여 둬서 여러 키를 함께 쓰는 방식으로 확장할 수 있다.
4. **이체 응답 안에서 바로 웹훅을 보내지 않은 이유는?**
   → 받는 쪽이 느리면 이체도 느려지고, 실패·재시작 시 다시 보낼 근거가 없다. 아웃박스에 적고 일꾼이 보낸다. 꼬리: *이체 성공과 아웃박스 저장 사이에 죽으면?* → 누락 가능(알려진 한계). 같은 키 재요청이나 대조 작업으로 보완.
5. **서버가 여러 대면 같은 알림을 두 번 보내지 않나요?**
   → `FOR UPDATE SKIP LOCKED`로 다른 일꾼이 잡은 줄은 건너뛴다. 일꾼 2개 동시 실행 테스트로 알림마다 정확히 1번을 확인했다. 꼬리: *HTTP 보내는 동안 잠금은?* → lease 시각만 바꾸고 바로 커밋해 잠금을 풀고 보낸다.
6. **받는 쪽은 서명을 어떻게 검증해야 하나요? 흔한 실수는?**
   → 받은 바이트 그대로 `타임스탬프.본문`의 HMAC을 계산해 상수 시간 비교. JSON을 다시 직렬화하면 서명이 맞지 않는다. 5분 지난 타임스탬프 거절, `X-Webhook-Id`로 중복 제거.
7. **웹훅은 정확히 한 번 전달되나요?**
   → 아니다. at-least-once. 처리 후 응답이 실패하면 다시 간다(`failAfterProcessing` 실험: 재전송 3번, 받은 기록 1건). 받는 쪽 중복 제거로 결과적으로 한 번 처리.
8. **웹훅 주소를 아무거나 등록할 수 있으면 어떤 문제가 있나요?**
   → SSRF. 내부망·메타데이터 주소로 요청을 보내게 만들 수 있다. 운영에서는 내부 주소 차단 + https만.
9. **화면에서 API 키 원문은 어떻게 다뤘나요?**
   → 발급 응답을 state에만 두고 모달로 1번 보여 준다. 닫으면 state에서 지운다. storage·console·URL에 남기지 않는다.
