# 1주차 정리 — 개발자 인증 · API 키 · bank_core 계좌 조회 연동

## 1. 목표

핀테크 앱이 **API 키 하나로 bank_core의 계좌를 조회**할 수 있는 최소 흐름을 끝까지 만든다.

```
개발자 회원가입/로그인(JWT) → 앱 등록 → API 키 발급 → X-API-Key로 /open/v1 호출 → bank_core 계좌 조회
```

- 개발자 포털 쪽 API(`/api/v1/**`)는 **JWT**로, 핀테크 앱이 부르는 오픈 API(`/open/v1/**`)는 **API 키**로 인증을 나눈다.
- 에러는 항상 같은 JSON 모양으로, 알맞은 상태 코드(400/401/403/404/405/409/502/504)로 돌려준다.
- Rate Limit, 사용량 집계, 웹훅, 프론트엔드는 2주차 이후로 미룬다.

## 4. 트러블슈팅

### 4-1. Spring Initializr가 500을 돌려줌
- **증상**: `curl`로 Initializr에 프로젝트 생성을 요청했더니 500 에러.
- **원인 찾기**: 옵션을 하나씩 빼면서 범위를 좁혔다. 의존성·자바 버전을 바꿔도 그대로였고, `bootVersion`만 바꾸자 해결됐다.
- **원인**: `bootVersion=4.1.3.RELEASE`처럼 옛날 표기(`.RELEASE`)를 썼다. Spring Boot는 2.x부터 `.RELEASE`를 붙이지 않는다.
- **해결**: `bootVersion=4.1.3`으로 요청.
- **교훈**: 원인을 모를 땐 "하나씩 바꿔 보며 범위 좁히기"가 가장 빠르다.

### 4-2. MySQL 3307 포트 충돌
- **증상**: Docker Compose로 MySQL을 띄우려니 포트가 이미 사용 중.
- **원인**: 같은 PC의 bank_core 프로젝트 MySQL 컨테이너(`bank-mysql`)가 3307을 쓰고 있었다.
- **해결**: 호스트 포트를 **3308**로 바꾸고 `127.0.0.1:3308:3306`처럼 **내 컴퓨터에만** 열었다. (IP를 생략하면 같은 와이파이의 다른 기기도 접속 가능)

### 4-3. 로그인 상태에서 없는 주소가 500
- **증상**: JWT를 넣고 없는 주소를 부르면 404가 아니라 500.
- **원인**: Spring이 "주소 없음"(`NoResourceFoundException`)이나 "메서드 틀림", "JSON 깨짐" 예외를 던지는데, 전역 예외 처리기가 이걸 모르는 예외로 보고 전부 500으로 바꿨다.
- **해결**: `GlobalExceptionHandler`에 404·405·400 처리를 추가하고 `ErrorHandlingTest`로 고정. (`67883eb`)

### 4-4. 실제 연동 때 502 — 요청이 nginx로 감
- **증상**: bank_core를 켰는데도 `/open/v1/accounts` 호출이 502.
- **원인 찾기**: `lsof -i :8080`으로 보니 8080을 **두 프로그램**이 잡고 있었다.
  - 로컬 **nginx** → 8080 **IPv4**(`127.0.0.1`)
  - **bank_core** → 8080 **IPv6**(`::1` / `*`)
  - bank-open-api는 `localhost:8080` → `127.0.0.1`(IPv4)로 접속 → bank_core가 아닌 **nginx**에 연결 → nginx가 502.
- **해결**: 쓰지 않던 nginx를 종료하자 정상 응답.
- **교훈**: "포트가 열려 있다 ≠ 내가 생각한 프로그램이 받는다". IPv4와 IPv6는 같은 포트 번호를 따로 쓸 수 있다.

### 4-5. bank_core DB가 비어 있음 (member 테이블 없음)
- **증상**: 연동 전용 회원을 bank_core DB에 넣으려 했는데 `member` 테이블이 없었다.
- **원인**: bank_core MySQL 컨테이너만 띄우고 bank_core 서버는 한 번도 안 켜서 **Flyway 마이그레이션이 실행되지 않았다**. (Flyway는 서버가 시작될 때 테이블을 만든다)
- **해결**: bank_core 서버를 한 번 켜서 마이그레이션을 실행 → 테이블 생성 후 회원 추가.

## 6. 알고 있는 한계

- **유효한 키만 있으면 연동 회원의 모든 계좌를 조회할 수 있다.**
  지금은 bank-open-api가 bank_core에 "연동 전용 회원" 한 명으로 로그인하므로, 어떤 앱이든 키만 있으면 그 회원이 가진 계좌는 전부 볼 수 있다. 앱별로 "이 앱은 이 계좌만" 같은 범위가 없다.
  실제 오픈뱅킹은 **고객이 직접 동의(OAuth)** 해서 앱마다 볼 수 있는 계좌 범위를 정한다.
- Rate Limit이 없어 키 하나로 무제한 호출이 가능하다. (2주차 예정)
- 사용량 기록이 없어 누가 얼마나 불렀는지 모른다. (2주차 예정)
- bank_core 토큰은 서버 메모리에 보관하므로 서버를 여러 대 띄우면 각자 따로 로그인한다.

## 7. 배운 개념

- **JWT vs API 키**: JWT는 사람이 로그인해서 받는 짧은 수명의 토큰, API 키는 서버(앱)가 오래 쓰는 비밀값. 쓰는 주체가 달라서 인증을 분리했다.
- **Security 필터 체인 여러 개**: `/open/v1/**`와 `/api/v1/**`에 서로 다른 `SecurityFilterChain`을 걸어 인증 방식을 나눈다.
- **비밀번호는 BCrypt, API 키는 SHA-256**: 비밀번호는 사람이 정해 추측 가능하니 일부러 느린 해시, API 키는 256비트 무작위라 추측 불가 + 요청마다 빠르게 찾아야 해서 빠른 해시 + UNIQUE 인덱스.
- **원문 1회 노출**: 키 원문은 발급 응답에서만 보여 주고 저장하지 않는다. DB가 유출돼도 키를 쓸 수 없다.
- **외부 시스템 에러 변환**: bank_core의 401/403/404/5xx/타임아웃을 우리 API 약속(404/502/504)으로 바꾼다. 내부 사정을 그대로 노출하지 않는다.
- **타임아웃**: 연결 3초·응답 5초. 상대가 느려도 우리 서버 스레드가 무한정 묶이지 않게 한다.
- **토큰 재사용 + 동시성**: 만료 전까지 토큰을 재사용하고, 동시에 여러 요청이 와도 `ReentrantLock` + "다시 확인"으로 로그인은 한 번만.
- **Flyway**: DB 테이블 구조를 버전 파일(`V1__`, `V2__` ...)로 관리하고 서버 시작 때 적용. `ddl-auto=validate`로 엔티티와 테이블이 맞는지만 검사.
- **Testcontainers**: 테스트 때 진짜 MySQL을 Docker로 띄워 H2 같은 가짜 DB와의 차이를 없앤다.
- **포트 바인딩과 IPv4/IPv6**: `127.0.0.1` 바인딩으로 외부 접근 차단, 같은 포트도 IPv4·IPv6가 따로 잡힐 수 있음.

## 8. 면접 꼬리 질문

1. **API 키를 왜 BCrypt가 아니라 SHA-256으로 저장했나요?**
   → 무작위 256비트라 무차별 대입이 불가능하고, 요청마다 검사해야 해서 빨라야 하며, 같은 입력이면 같은 해시가 나와야 인덱스로 바로 찾을 수 있다.
   - 꼬리: *그럼 DB가 유출되면?* → 해시만 있으므로 원문을 알 수 없다. 원문은 발급 때 한 번만 보여 준다.
2. **JWT와 API 키 인증을 왜 나눴나요?**
   → 쓰는 주체(사람 vs 서버)와 수명·폐기 방식이 다르다. 필터 체인을 경로별로 분리해 서로 섞이지 않게 했다.
3. **bank_core가 403과 404를 줄 때 왜 둘 다 404로 바꿨나요?**
   → 403을 그대로 주면 "그 계좌는 존재한다"는 정보가 새어 나간다(계좌 번호 찍어 보기 공격).
4. **bank_core가 느리거나 꺼지면 어떻게 되나요?**
   → 연결 3초·응답 5초 타임아웃, 꺼짐은 502, 느림은 504. 꼬리: *계속 느리면?* → 다음 단계로 서킷 브레이커를 생각하고 있다.
5. **토큰이 만료되면? 동시에 100개 요청이 오면?**
   → 만료 30초 전 갱신, 401이면 1회만 재발급 후 재시도. 자물쇠 + 다시 확인으로 로그인은 한 번만.
6. **지금 구조의 보안 한계는?**
   → 키만 있으면 연동 회원의 모든 계좌 조회 가능. 실제 오픈뱅킹은 고객 동의 OAuth로 앱별 계좌 범위를 정한다.
7. **502가 났을 때 어떻게 원인을 찾았나요?**
   → `lsof`로 8080을 누가 잡고 있는지 확인 → nginx(IPv4)와 bank_core(IPv6)가 같이 잡고 있었음을 발견.
8. **AI 에이전트를 어떻게 썼나요? 결과를 어떻게 믿었나요?**
   → 설계·보안 규칙은 내가 정하고 코드 작성을 맡겼다. 테스트 56개와 실제 curl 연동으로 검증했고, 트러블슈팅은 원인을 직접 확인했다.
